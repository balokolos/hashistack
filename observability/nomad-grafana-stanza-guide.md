# Nomad Job Stanzas: Grafana Example

This guide explains the main Nomad job stanzas used by the Grafana job in this directory.
The example runs Grafana with Docker, stores its data in a Nomad host volume, registers
Grafana in Consul, exposes it through Traefik, and uses Consul Connect to reach
Prometheus and Loki.

## Complete example

```hcl
job "grafana" {
  datacenters = ["dc1"]
  type        = "service"

  group "grafana" {
    count = 1

    network {
      mode = "bridge"

      port "http" {
        to = 3000
      }
    }

    volume "grafana-data" {
      type      = "host"
      source    = "grafana-data"
      read_only = false
    }

    service {
      name     = "grafana"
      port     = "http"
      provider = "consul"

      tags = [
        "traefik.enable=true",
        "traefik.http.routers.grafana.rule=Host(`grafana.balokolos.com`)",
        "traefik.http.routers.grafana.entrypoints=websecure",
        "traefik.http.routers.grafana.tls=true",
      ]

      connect {
        sidecar_service {
          tags = ["traefik.enable=false"]

          proxy {
            upstreams {
              destination_name = "prometheus"
              local_bind_port  = 9090
            }

            upstreams {
              destination_name = "loki"
              local_bind_port  = 3100
            }
          }
        }
      }

      check {
        type     = "http"
        path     = "/api/health"
        interval = "10s"
        timeout  = "3s"
      }
    }

    task "grafana" {
      driver = "docker"

      config {
        image = "grafana/grafana:latest"

        ports = [
          "http",
        ]
      }

      volume_mount {
        volume      = "grafana-data"
        destination = "/var/lib/grafana"
      }

      env {
        GF_SECURITY_ADMIN_USER     = "admin"
        GF_SECURITY_ADMIN_PASSWORD = "admin"
      }

      resources {
        cpu    = 500
        memory = 512
      }
    }
  }
}
```

## `job` stanza

```hcl
job "grafana" {
  datacenters = ["dc1"]
  type        = "service"
}
```

The `job` stanza is the top-level definition submitted to Nomad.

### Job name

`grafana` is the job ID. It is used in commands such as:

```bash
nomad job status grafana
nomad job run grafana.nomad
```

The job ID must be unique within the Nomad namespace and region.

### `datacenters`

```hcl
datacenters = ["dc1"]
```

This limits placement to Nomad clients in the `dc1` datacenter. If no eligible
client exists in that datacenter, the job remains pending.

### `type`

```hcl
type = "service"
```

A service job is intended to run continuously and provide an application or API.
Nomad maintains the desired count and uses the service health check during deployment.

Common job types include:

- `service`: long-running applications.
- `batch`: finite work that eventually completes.
- `system`: one allocation on every eligible client, commonly used for agents.
- `sysbatch`: batch-style work placed across eligible clients.

## `group` stanza

```hcl
group "grafana" {
  count = 1
}
```

A task group is a set of tasks that are scheduled together on the same Nomad client
and share networking, volumes, and lifecycle behavior.

The Grafana group contains:

- The Grafana Docker task.
- The automatically created Consul Connect sidecar task.
- The group network namespace.
- The Grafana data volume.
- The Grafana Consul service registration.

### `count`

```hcl
count = 1
```

Nomad creates one allocation of this group. Increasing it creates multiple Grafana
instances, but the data volume and external routing strategy must then support that
layout.

## `network` stanza

```hcl
network {
  mode = "bridge"

  port "http" {
    to = 3000
  }
}
```

The group network defines how tasks communicate and which ports Nomad allocates.

### `mode = "bridge"`

Bridge networking gives the allocation its own network namespace while allowing the
Grafana task and Connect sidecar to communicate through `localhost`.

Connect sidecars require `bridge` or a supported `cni/*` network mode. Host networking
cannot be used for this Connect-enabled group.

### Port label

```hcl
port "http" {
  to = 3000
}
```

`http` is a logical port label. Other stanzas refer to it by name:

```hcl
service {
  port = "http"
}

config {
  ports = ["http"]
}
```

The `to` value is the port where Grafana listens inside the allocation. Nomad assigns
the host-side port dynamically unless `static` is specified.

Grafana should use port `3000` inside the container. Traefik and Consul use the
registered service address and port generated by Nomad.

## `volume` stanza

```hcl
volume "grafana-data" {
  type      = "host"
  source    = "grafana-data"
  read_only = false
}
```

This declares a volume that the task group can mount.

### `type = "host"`

The volume comes from a host volume configured on the Nomad client. The source is
not an arbitrary path in the job; it must match a configured Nomad host volume.

Example client configuration:

```hcl
client {
  host_volume "grafana-data" {
    path      = "/opt/monitoring/grafana/data"
    read_only = false
  }
}
```

### `source`

```hcl
source = "grafana-data"
```

This references the host volume by its Nomad configuration name.

### `read_only`

```hcl
read_only = false
```

Grafana must write its database, plugins, and configuration state, so the volume is
writable. The host directory must also have permissions that allow the Grafana
container user to write.

## `service` stanza

```hcl
service {
  name     = "grafana"
  port     = "http"
  provider = "consul"
}
```

The service stanza registers Grafana in a service discovery system. In this job,
Nomad registers it with Consul.

### `name`

```hcl
name = "grafana"
```

This is the Consul service name. Other Connect services use this name as their
`destination_name`.

### `port`

```hcl
port = "http"
```

This connects the service registration to the group port label. It tells Consul to
advertise the port where the Grafana application listens.

### `provider`

```hcl
provider = "consul"
```

Nomad uses Consul for service registration and health state. This is required for the
Consul Catalog provider in Traefik and for Consul Connect service discovery.

## Traefik `tags`

```hcl
tags = [
  "traefik.enable=true",
  "traefik.http.routers.grafana.rule=Host(`grafana.balokolos.com`)",
  "traefik.http.routers.grafana.entrypoints=websecure",
  "traefik.http.routers.grafana.tls=true",
]
```

These tags are metadata read by Traefik's Consul Catalog provider.

- `traefik.enable=true` enables discovery for Grafana.
- The `rule` routes requests whose host is `grafana.balokolos.com`.
- `entrypoints=websecure` selects Traefik's HTTPS entrypoint.
- `tls=true` enables TLS handling for the router.

The Connect sidecar must not inherit these router tags. Otherwise Traefik sees both
`grafana` and `grafana-sidecar-proxy` with the same router name. The sidecar therefore
uses:

```hcl
tags = ["traefik.enable=false"]
```

Traefik must also have Consul Connect awareness enabled:

```text
--providers.consulcatalog.connectaware=true
```

## `connect` stanza

```hcl
connect {
  sidecar_service {
    tags = ["traefik.enable=false"]

    proxy {
      upstreams {
        destination_name = "prometheus"
        local_bind_port  = 9090
      }

      upstreams {
        destination_name = "loki"
        local_bind_port  = 3100
      }
    }
  }
}
```

This enables Consul Connect for Grafana. Nomad creates a sidecar proxy task in the
same allocation. The Grafana task sends requests to local ports, and the sidecar
forwards those requests through the Connect mesh.

### `sidecar_service`

```hcl
sidecar_service {
  tags = ["traefik.enable=false"]
}
```

Nomad creates and manages the sidecar lifecycle with the application allocation.
The sidecar has its own Consul registration, normally named
`grafana-sidecar-proxy`.

### `proxy`

The `proxy` block defines Connect proxy behavior, including upstream services.

### `upstreams`

```hcl
upstreams {
  destination_name = "prometheus"
  local_bind_port  = 9090
}
```

This creates a local listener at `localhost:9090` in the allocation. Requests sent
to that port travel through Connect to the Consul service named `prometheus`.

Grafana's Prometheus datasource should therefore use:

```text
http://localhost:9090
```

The Loki upstream follows the same pattern:

```hcl
upstreams {
  destination_name = "loki"
  local_bind_port  = 3100
}
```

Grafana's Loki datasource should use:

```text
http://localhost:3100
```

Both destination services need their own Connect sidecars and must have an allowed
Consul intention from `grafana` to the destination service.

## `check` stanza

```hcl
check {
  type     = "http"
  path     = "/api/health"
  interval = "10s"
  timeout  = "3s"
}
```

The check tells Consul and Nomad whether Grafana is healthy.

- `type = "http"`: perform an HTTP request.
- `path`: request Grafana's health endpoint.
- `interval`: run the check every 10 seconds.
- `timeout`: fail an individual check after 3 seconds.

A passing check allows the service to receive traffic and allows a deployment to be
marked healthy.

## `task` stanza

```hcl
task "grafana" {
  driver = "docker"
}
```

A task is an executable unit inside the group. This task runs the Grafana container.

### `driver`

```hcl
driver = "docker"
```

Nomad uses its Docker task driver to pull and run the Grafana image. The Nomad client
must have Docker available and the Docker driver enabled.

## `config` stanza

```hcl
config {
  image = "grafana/grafana:latest"

  ports = [
    "http",
  ]
}
```

The Docker driver configuration controls how the container starts.

### `image`

```hcl
image = "grafana/grafana:latest"
```

Nomad asks Docker to run this image. For repeatable deployments, use a fixed version
rather than `latest`, for example `grafana/grafana:12.1.0`.

### `ports`

```hcl
ports = ["http"]
```

This exposes the group network port named `http` to the Docker task. The port label
must exist in the group `network` stanza.

## `volume_mount` stanza

```hcl
volume_mount {
  volume      = "grafana-data"
  destination = "/var/lib/grafana"
}
```

This mounts the declared Nomad volume inside the container.

- `volume` references the group volume declaration.
- `destination` is the path Grafana uses for its database and persistent data.

The volume must be writable. A permission failure here commonly appears as Grafana
being unable to create or update files under `/var/lib/grafana`.

## `template` stanza: create a local config file

Nomad can render a configuration file into the allocation's local directory before
the task starts. This lets the job create application configuration without manually
copying files to the Nomad client.

For example, add a `template` stanza inside the Grafana task:

```hcl
task "grafana" {
  driver = "docker"

  config {
    image = "grafana/grafana:latest"

    args = [
      "--config=/local/grafana.ini",
    ]
  }

  template {
    destination = "local/grafana.ini"
    change_mode = "restart"

    data = <<EOF
[server]
http_port = 3000
domain = grafana.balokolos.com

[security]
admin_user = admin
EOF
  }
}
```

### `destination`

```hcl
destination = "local/grafana.ini"
```

This is the path inside the allocation where Nomad writes the rendered file. The
`local/` directory belongs to the allocation and is available to the task. It is not
the same as a host volume.

### `data`

```hcl
data = <<EOF
[server]
http_port = 3000
EOF
```

The heredoc contains the file contents. Nomad writes it to `destination` before the
task starts. Template functions and values from Consul or Vault can also be used when
configuration must be generated dynamically.

### `change_mode`

```hcl
change_mode = "restart"
```

This controls what happens when the rendered content changes:

- `restart`: restart the task so the application reloads the file.
- `signal`: send a signal configured by `change_signal`.
- `noop`: update the file without restarting the task.

Use `restart` when the application reads configuration only during startup. Use
`signal` or `noop` only when the application supports live reloads.

### Use the rendered file in the application

The application must be configured to read the same path that Nomad renders. In the
example, the Docker task passes the path through Grafana's command-line arguments:

```hcl
config {
  image = "grafana/grafana:latest"

  args = [
    "--config=/local/grafana.ini",
  ]
}
```

The rendered file and the application argument are separate concerns:

1. `template.destination` creates the file.
2. `config.args` tells the application to read the file.
3. `change_mode` determines how configuration changes reach the application.

### Check the rendered file

After the allocation starts, inspect the file from the task:

```bash
nomad alloc exec -task grafana <allocation-id> \\
  sh -c 'cat /local/grafana.ini'
```

Inspect the task status and logs if the file is missing or Grafana fails to start:

```bash
nomad alloc status <allocation-id>
nomad alloc logs <allocation-id> grafana
```

Do not place production passwords or API tokens directly in the heredoc. Use Vault
templates or Nomad variables for secret values, and apply appropriate permissions to
the rendered file.

## `env` stanza

```hcl
env {
  GF_SECURITY_ADMIN_USER     = "admin"
  GF_SECURITY_ADMIN_PASSWORD = "admin"
}
```

These environment variables are passed to the Grafana container. Grafana uses them
to initialize the admin account.

Do not store real production passwords directly in a job file. Use Vault, Nomad
variables, or another secret-management mechanism instead.

## `resources` stanza

```hcl
resources {
  cpu    = 500
  memory = 512
}
```

This declares the resources Nomad should reserve for the task.

- `cpu = 500`: reserve 500 MHz of CPU.
- `memory = 512`: reserve 512 MB of memory.

If no client has enough available resources, Nomad cannot place the allocation.

## Useful commands

Validate the job before submitting it:

```bash
nomad job validate grafana.nomad
```

Preview scheduling and configuration changes:

```bash
nomad job plan grafana.nomad
```

Run the job:

```bash
nomad job run grafana.nomad
```

Inspect the job and allocation:

```bash
nomad job status grafana
nomad job allocations grafana
nomad alloc status <allocation-id>
```

Inspect task logs:

```bash
nomad alloc logs <allocation-id> grafana
nomad alloc logs <allocation-id> connect-proxy-grafana
```

Check the registered service and Connect proxy:

```bash
curl -s http://127.0.0.1:8500/v1/catalog/service/grafana | jq
curl -s http://127.0.0.1:8500/v1/catalog/service/grafana-sidecar-proxy | jq
```

## Important relationships

The Grafana job works because these names and ports line up:

| Caller | Local address | Connect destination | Destination service |
|---|---:|---|---|
| Grafana | `localhost:9090` | `prometheus` | Prometheus Connect service |
| Grafana | `localhost:3100` | `loki` | Loki Connect service |
| Traefik | Consul Catalog | `grafana` | Grafana application service |

For a Connect upstream to work, the following must all be true:

1. The caller has a Connect sidecar and upstream definition.
2. The destination is registered in Consul.
3. The destination has a Connect sidecar.
4. The caller-to-destination Consul intention is allowed.
5. The local bind port is not already used by another upstream.
6. The destination application listens on the port configured in its Nomad network stanza.
